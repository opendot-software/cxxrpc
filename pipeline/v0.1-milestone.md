# cxxrpc v0.1 Milestone

## Milestone Purpose

`v0.1` is the first working vertical slice of the OpenDot `cxxrpc` runtime.

The goal is **not** to implement the complete long-term runtime, plugin ecosystem, GUI, Python bindings, distributed execution, or accelerator support.

The goal is to prove one narrow and useful proposition:

> **A programmer can construct a reliable native C++ processing pipeline while `cxxrpc` handles thread lifecycle, bounded data passing, CPU affinity, shutdown, and basic runtime observability.**

This release should be small, predictable, testable, and suitable as the foundation for later versions.

---

# Primary Goal

Deliver a usable C++20 pipeline runtime capable of executing a linear multi-stage processing pipeline on Linux.

A target programming model should resemble:

```cpp
using namespace opendot;

cxxrpc::pipeline<image> image_processing;

image_processing
    .stage("load", load_image)
    .workers(1)
    .cores({0});

image_processing
    .stage("grayscale", grayscale)
    .workers(1)
    .cores({1});

image_processing
    .stage("blur", blur)
    .workers(1)
    .cores({2});

image_processing
    .stage("edges", edge_detection)
    .workers(1)
    .cores({3});

image_processing.connect("load", "grayscale", 32);
image_processing.connect("grayscale", "blur", 32);
image_processing.connect("blur", "edges", 32);

image_processing.run();
```

The exact API may change during implementation, but the developer experience should remain similarly concise.

---

# v0.1 Success Criteria

`v0.1` is successful if all of the following are true:

- [ ] A user can define an arbitrary-length **linear pipeline**.
- [ ] Each stage can execute on its own worker thread.
- [ ] Data moves between stages through bounded channels.
- [ ] Channels support backpressure through blocking behavior.
- [ ] Move-only data types can pass through the pipeline.
- [ ] Worker threads are created and managed automatically.
- [ ] The pipeline can terminate cleanly after processing completes.
- [ ] The pipeline can be stopped without deadlocking blocked workers.
- [ ] Exceptions or fatal stage failures are propagated to the runtime.
- [ ] A stage can be assigned to one or more requested CPU cores.
- [ ] Basic per-stage execution statistics are collected.
- [ ] Pipeline throughput can be reported.
- [ ] The runtime is covered by unit and integration tests.
- [ ] The runtime passes concurrency-focused sanitizer testing.
- [ ] At least one non-trivial image-processing demonstration exists.
- [ ] A manually implemented equivalent pipeline is available for benchmarking.
- [ ] The `cxxrpc` implementation demonstrates meaningfully less concurrency boilerplate than the manual implementation.
- [ ] The project builds and tests automatically through CI.

# Scope

## In Scope

### Core Pipeline API

The user must be able to:

- create a pipeline
- add stages
- connect stages
- configure channel capacity
- configure stage CPU affinity
- start execution
- wait for execution
- stop execution cleanly
- inspect basic performance statistics

### Stage Execution

For `v0.1`:

- one worker thread per stage is sufficient
- stage logic is supplied through C++ callables, functions, functors, or a simple stage abstraction
- stages execute independently
- stage infrastructure must not require users to directly manage threads
- runtime-created threads must have well-defined ownership and lifetime

### Linear Pipeline Topology

Supported:

```text
A -> B -> C -> D -> E
```

Not required:

```text
        +-> C -+
A -> B -|      |-> F
        +-> D -+
```

General DAG execution is deliberately postponed.

### Bounded Channels

Channels between stages must provide:

- finite capacity
- blocking `push` when full
- blocking `pop` when empty
- shutdown-aware waiting
- move semantics
- safe destruction
- no unbounded memory growth

Conceptually:

```text
Stage A
   |
   v
+----------------+
| bounded queue  |
| capacity = 32  |
+----------------+
   |
   v
Stage B
```

### Backpressure

The required `v0.1` backpressure policy is:

```text
BLOCK
```

If a downstream stage cannot keep up, the upstream producer eventually blocks when the channel reaches capacity.

Policies such as `drop_oldest`, `drop_newest`, `overwrite`, and `adaptive` are post-MVP features.

### CPU Affinity

The runtime should provide a portable framework abstraction but may use a Linux-specific implementation internally for `v0.1`.

Example:

```cpp
stage.cores({2});
```

The runtime should verify or report affinity failures rather than silently ignoring them.

### Runtime Lifecycle

At minimum, support:

```text
construct
configure
start/run
normal completion
stop
join
destroy
```

The runtime must avoid abandoned worker threads, use-after-free during shutdown, deadlocks caused by blocked channels, and infinite waits after upstream completion.

### Error Propagation

A fatal exception in one stage should not leave the remaining pipeline hanging indefinitely.

The runtime should:

1. record the error
2. initiate pipeline shutdown
3. unblock waiting stages
4. join managed threads
5. report or rethrow the failure to the application

Sophisticated recovery and stage restart behavior are not required.

### Basic Metrics

Each stage should expose:

```text
items processed
total processing time
average processing time
input wait time
output wait time
```

Pipeline-level metrics:

```text
wall-clock execution time
total items completed
throughput
```

Optional if straightforward:

```text
minimum stage time
maximum stage time
queue high-water mark
```

# What to Expect from v0.1

Users should expect:

- a small native C++ runtime
- a simple pipeline programming model
- predictable CPU execution and explicit affinity
- bounded memory behavior under slow consumers
- basic observability for bottleneck discovery
- minimal runtime dependencies

Application stage code should focus primarily on algorithms rather than thread, queue, shutdown, or affinity management.

---

# What NOT to Expect from v0.1

The following are deliberately out of scope:

- no GUI / Pipeline Studio
- no dynamic `.so` plugin loading
- no Python bindings
- no MPI
- no multi-process runtime
- no GPU runtime
- no general DAG scheduler
- no automatic load balancing
- no multiple workers per stage
- no stable binary plugin ABI guarantee
- no production security model for untrusted stage code

All `v0.1` execution occurs within one process and targets a simple linear CPU pipeline.

## Demo 1 — Minimal Pipeline

Purpose: prove the API is easy to understand.

```text
source
  |
  v
multiply_by_two
  |
  v
add_one
  |
  v

```

Success criterion:

## Demo 2 — Image Processing Pipeline

Primary MVP demonstration:

```text
Load image
    |
    v
Grayscale
    |
    v
3x3 Blur
    |
    v
Sobel Edge Detection
    |
    v
Write image
```

Prefer a simple image format such as PPM initially if it avoids unnecessary dependencies.

The demo should show:

- stage creation
- stage connections
- bounded channels
- CPU affinity
- output correctness
- runtime metrics

## Demo 3 — Backpressure

```text
Fast Producer
     |
     v
Queue capacity = 8
     |
     v
Slow Consumer
```

Show that:

- queue memory remains bounded
- producer eventually blocks
- pipeline remains correct
- metrics reflect waiting/backpressure

## Demo 4 — CPU Affinity

```text
Stage A -> CPU 0
Stage B -> CPU 1
Stage C -> CPU 2
Stage D -> CPU 3
```

Demonstrate that the runtime applies the mapping successfully.

## Demo 5 — Failure and Clean Shutdown

Create a stage that intentionally throws after processing some number of items.

Verify that:

- the pipeline terminates
- blocked channels wake up
- worker threads join
- the application receives a useful failure
- the process does not hang

# Required Benchmarks

The benchmark goal is not only maximum performance.

The MVP must test the claim:

> **`cxxrpc` can provide comparable pipeline execution performance while significantly reducing the amount of concurrency-management code required from the application programmer.**

## Benchmark A — Manual vs cxxrpc Pipeline

Implement the same pipeline twice.

### Baseline

Hand-written using:

```text
std::thread / std::jthread
mutexes
condition variables
bounded queues
thread lifecycle
CPU affinity
shutdown handling
statistics
```

### cxxrpc Version

Use the framework's public API.

Compare:

```text
total runtime
throughput
latency if practical
CPU utilisation
source lines of code
concurrency-related lines of code
```

## Benchmark B — Pipeline Scaling by Number of Stages

Test:

```text
2 stages
4 stages
8 stages
```

Use controlled synthetic work per stage.

Measure:

```text
throughput
per-stage processing time
runtime overhead
```

## Benchmark C — Channel Capacity

Test representative channel capacities:

```text
1
8
32
128
```

Measure:

```text
throughput
producer wait time
consumer wait time
memory behavior
```

## Benchmark D — Balanced vs Imbalanced Pipeline

Balanced:

```text
A 1ms -> B 1ms -> C 1ms
```

Imbalanced:

```text
A 1ms -> B 5ms -> C 1ms
```

Measure:

```text
throughput
queue behavior
input wait time
output wait time
```

The metrics should clearly identify stage B as the bottleneck.

## Benchmark E — Affinity On vs Off

Where practical, compare scheduler-selected placement against explicit CPU pinning.

The goal is to validate affinity control and establish a methodology for later versions, not to make broad hardware-independent performance claims from one machine.

# Definition of Done

The milestone is complete when a developer unfamiliar with the internals can:

1. clone the repository
2. build it using documented commands
3. run the minimal example
4. build a small custom pipeline
5. assign stages to CPU cores
6. run the image-processing demo
7. observe per-stage metrics
8. see backpressure in an imbalanced example
9. compare the framework implementation with the manual baseline
10. understand what `v0.1` deliberately does and does not provide

---

# Core v0.1 Product Claim

> **OpenDot `cxxrpc::pipeline` provides a small, reliable C++20 abstraction for building CPU processing pipelines with automatic thread management, bounded communication, CPU affinity, clean lifecycle handling, and basic observability—without requiring application programmers to repeatedly implement the underlying concurrency infrastructure themselves.**
